# ADR-001 — WASM Component Model, WIT interface and host runtime

**Status:** PROPOSED — local validation passed; hosted Linux CI acceptance pending
**Version:** 0.1 · 2026-10-15
**Scope:** The initial stateless computation ABI and its Rust host
**Related:** Architecture/Interface v0.1 §5.4; Component Package/Manifest v0.1 §4; ADR-002, ADR-007, ADR-008

## Context
The Workbench must run third-party computational components with stable typed entry points, independent of Qt, while the trusted host controls capabilities, message routing and persistence. The upstream architecture proposes a Component Model component exporting a WIT `computation` interface. The package contract names the runtime as `wasm-component` and requires `runtime.interface = "org.workbench.component@0.1"`. This is a *manifest-level ABI discriminator*; it is **not** itself a WIT package identifier.

## Decision (proposed)
1. **Binary model:** use WebAssembly **Component Model**, not bare core WASM modules as the public interface. Reject modules that are not valid components or do not match the expected exported WIT world.
2. **Interface definition:** use the WIT package `workbench:component@0.1.0`, world `compute-component`, exporting interface `computation`. Keep the exact WIT in `wit/component.wit`, and use it as the source of truth for generated guest and host bindings.
3. **Host runtime:** use **Wasmtime Rust embedding API** and `wasmtime::component::bindgen!` for initial native host implementation. Locally tested Cargo dependency `wasmtime = "=49.0.1"` with default features for spike simplicity, Rust `1.99.1`, cargo-component `0.21.1`, guest wit-bindgen-rt `0.41.0`. Native and guest lockfiles and toolchain file pin the tested inputs. Hosted Linux CI acceptance is still pending; see the linked evidence.
4. **Execution:** v0.1 synchronous `compute(message) -> result<list<message>, component-error>` with JSON payload encoded as UTF-8 string. One call corresponds to one independently validated input event. The host handles JSON Schema validation before and after the call; port/semantic matching is outside WIT.
5. **Privileges:** pure v0.1 compute world **imports no filesystem, network, clocks, random, process or host capability APIs**. The linker MUST NOT supply ambient WASI imports. Capability-bearing and stateful worlds require separate ADRs and interface versions.
6. **Errors:** distinguish component-reported errors (`result::err`) from engine traps and host validation failures. A component result is not a host-authorized event. Route it through output-schema and permission checks.
7. **Compatibility:** freeze the WIT source and its content hash when G1 passes. Manifest runtime identifier remains `org.workbench.component@0.1`; WIT package remains `workbench:component@0.1.0`. No untested assertion of cross-runtime compatibility.
8. **Asynchrony:** exclude WASI 0.3 `future`, `stream`, async canonical ABI and resource handles from this world. Use host-side scheduling initially; revisit for streaming workloads later.

## Chosen v0.1 WIT
See `wit/component.wit`. WIT field types are strings/lists, not arbitrary JSON values. The host MUST parse and schema-validate JSON payloads; the WIT signature alone cannot assert decimal precision, semantics or units.

## Alternatives
| Alternative | Benefit | Reason not selected for v0.1 |
|---|---|---|
| Core WASM with custom byte-buffer ABI | Potentially small/runtime-agnostic | Must invent lifting/lowering, language bindings, interface discovery and compatibility |
| Extism or another plugin SDK | Convenience | Adds an SDK/ABI layer that obscures target Component Model guarantees |
| WASI command (`wasi:cli/command`) per invocation | Easy CLI integration | Process-oriented, poor fit for reusable typed callable components |
| WASI 0.3 async component world | Native futures/streams | More moving parts before simple vertical slice is proven |
| Wasmer or alternative host | Potential portability/cost benefits | Requires separate conformance spike; not rejected long-term |

## Security and failure model
- Component Model typing is an interoperability mechanism, **not** a security guarantee.
- Guest receives no host imports. Configure memory limits, fuel/epoch interruption and timeouts before admitting untrusted modules; the spike validates the concrete execution budgets below, not general hostile-package admission or a production numerical workload policy.
- Treat malformed component, incorrect world, traps, oversized payloads, unexpectedly large result lists and invalid JSON/schema as non-successful calls with structured errors.
- Host allocates separate `Store` per isolated instance (or an isolation-equivalent design backed by tests); component instances are never directly exposed to QML.
- No automatic retry of side-effecting operations is relevant to the pure v0.1 world.
- Run all generated code in non-privileged test environments; host operations such as source editing and compilation belong to later capability worlds.

| ID | Test | Pass condition |

| ABI-006 | Reported error/trap | Guest error remains distinct from trap; host survives both |

| ABI-009 | Bundle manifest | Valid module digest, `runtime.kind` and `runtime.interface` match package contract; tampered bytes rejected |
| ABI-010 | Reproducibility | CI records exact Rust/Wasmtime/cargo-component versions and lockfile, and runs all tests |

Optional evidence: execute guest under a second Component Model runtime. Until then promise **Wasmtime compatibility**, not universal runtime compatibility.

## Spike procedure
1. Install Rust and `cargo-component`, record `rustc -V`, `cargo -V`, `cargo component -V` and operating system; the exact versions used must be committed as an evidence report.
2. Generate Rust guest bindings from `wit/component.wit`; compile the example guest as a *component*, not `wasm32-wasi` core module. Confirm cargo-component's current CLI and target installation instructions in its documentation, rather than assuming a fixed command across releases.
3. Compile host using pinned Wasmtime dependency and generated bindings.
4. Run the acceptance matrix, capture logs and hashes, then set the version pin in the parent repository and mark ADR-001 ACCEPTED only if tests pass.

## Consequences
- Clear WIT-first boundary between component implementation and kernel.
- JSON remains the fixture and schema validation format; double serialization is accepted for v0.1 simplicity.
- Streaming, resources and host imports are explicit future contract revisions, not ad hoc payload conventions.
- Upgrade Wasmtime behind the host adapter while requiring guest compatibility regression tests.

## Local spike evidence (2026-10-15)

See [executed results and reproduction commands](evidence/ADR-001-results.md).
The positive echo/integer guests and the deliberately disallowed WASI guest were
compiled independently. ABI-001..009 and local ABI-010 reproduction checks pass;
ABI-010's hosted Linux CI run remains unexecuted. The required workspace formatting
check fails in unchanged scaffold crates. **Do not infer Accepted status from local
test names or a configured workflow.** No remote is configured to submit/run CI.

The spike uses separate stores per event, no linker imports, explicit generated-type
signature checks before instantiation, 8 MiB memory, 2,000,000 fuel, 100 10ms epoch
ticks, 16 KiB message/batch data and eight-result limits. Error regressions cover
resource-count limits as well as growth, fuel and epoch failures. Component
compilation and native output lifting require additional production resource policy.

The WIT SHA-256 is `cf90e5114153e2737accd1fc7535e1e494e699ac68b4e99e8cc36c8270a204c0`;
it is recorded for this spike, not frozen as an Accepted G1 contract. Manifest,
ontology, kernel permission defaults and semantic compatibility rules are unchanged.

## Unresolved before acceptance
1. Which exact Wasmtime/cargo-component/Rust versions pass a reproducible CI run?
2. What concrete memory/fuel/epoch limits are appropriate for untrusted numerical components?
3. Should validation use a separate published guest bindings package or generate from a vendored WIT source?
4. What feature/platform matrix (Linux/Windows/macOS) will be tested before external alpha?
