# ADR-005 — Operator Agent, Intent Resolution and Composition Planning

**Status:** Accepted — scoped Linux offline single-component profile; [verified evidence](../implementation/adr-005/evidence/RESULTS.md)
**Version:** 0.1 · 2026-10-27
**Owners:** agent orchestration, contracts, semantic registry, kernel, security, desktop Qt, verification
**Prerequisites:** Accepted ADR-001–004, VSLICE-001–002 (Linux); existing Architecture and Interface Specification v0.1 and frozen `planVersion: "0.1"` contract.

## 1. Context and objective

The Workbench already admits immutable components, executes pure-WASM via accepted WIT, applies room-local plans and reactive state with revision fences, and presents a persistent semantic Qt canvas. A human currently selects installed components. The next capability is an **Operator** which transforms a user's explicit request into a reviewed, machine-validatable proposal to reuse an installed component and initialise its inputs. Operator MUST NOT become an alternative executor, permission authority, metadata trust root, or a high-frequency reactive scheduler.

The first end-to-end use case is: “I need a mortgage calculator for a £250,000 loan over 25 years at 5%.” Operator discovers the already-installed mortgage calculator, produces a proposal referring to its **actual** immutable pin and admitted UI, then the host validates/applies it and submits correctly typed initial inputs via the accepted ingress path. No new calculator or UI is generated.

## 2. Decision (normative for this proposal)

1. **Separate four stages:** (a) human intent/parameter extraction, (b) trusted read-only local registry discovery, (c) untrusted structured proposal by a replaceable provider, and (d) host validation/authorisation/atomic application. There is no direct model-to-kernel write channel.
2. **Keep executable plans on the established `planVersion: "0.1"` contract.** Never bypass existing kernel plan validation, room revision checks, capability policy, installation trust, or UI admission. Do not add an Operator-specific WASM ABI, guest import, Qt evaluation feature, or router.
3. **Bound the first planner to one new locally installed component and one existing room.** No remote component fetch, code generation, multi-component synthesis, parallel agent tools, speculative installation, privilege request, or silent update. Initial parameter submission is a distinct, schema-checked host operation after successful topology application; it is *not* smuggled into an unrecognised plan field.
4. **Provider abstraction:** a typed Rust async `OperatorProvider` interface accepts a minimised task and host-supplied candidate catalog and returns a bounded response. Support a deterministic fixture provider for CI and one optional configurable model adapter. Provider is replaceable; no untrusted provider output is ever considered validated merely because it is structured JSON.
5. **Catalog as data, not instructions:** host creates bounded discovery candidates from admitted registry records; model receives only identifiers, versions, digests, semantically relevant capability/port descriptions, local UI availability and minimal schema summaries. No arbitrary package README/RDF literal is elevated to an instruction. Reject malformed metadata or mark candidate unavailable; do not leak paths, secrets, or room history unrelated to the explicit request.
6. **Host owns candidate selection and revalidation:** an Operator response must select an ID/version/SHA present in the offered candidate set and still resolve that exact immutable pin at apply time. No substring, loose version, or label-based matching. The host reconciles all references with the admitted manifest, RDF, input schemas and UI binding definitions.
7. **Two-step proposal/commit:** `prepare` yields a preview containing the selected capability, extracted inputs, exact pin, effects, and whether authorisation is needed. `apply` requires a fresh user-originated approval token bound to a proposal hash, room ID/revision, expiry, and intended action; a safe, explicitly enabled policy MAY auto-approve the narrow local zero-permission case. Default v0.1 uses explicit confirmation. Revocation or drift invalidates the approval.
8. **No silent fallback:** ambiguity, no match, invalid required parameters, unsupported plan structure, timeout, provider failure, candidate drift, stale room revision and user rejection produce typed outcomes and *no topology/state mutation*. A clarification is requested when needed; never invent a rate, term, monetary unit or permissions.
9. **Treat initialization independently:** after atomic topology commit, initial edits use the accepted typed ingress and computed results go through the real WASM/bus. On ingress failure after plan commit, report partial *workflow* completion truthfully and offer an explicit recovery action; never claim cross-stage atomicity that the current runtime does not provide. UI never shows a value as committed until the host reports a successful commit.
10. **No Operator in the reactive path:** later slider edits, restore, navigation and rendering are handled by accepted deterministic mechanisms. Network/model access is optional and unavailable during offline restoration.
11. **Telemetry and privacy:** model endpoint, invocation token/time budgets, payload limits, redaction, correlation and audit data are host-owned. Do not store provider secrets in room snapshots, transmit arbitrary stored documents, or log full raw user prompts by default. Audit proposal digest, selected pin, provider kind, validation/approval/application status, revision and error codes.
12. **Retries are bounded and explicit:** at most one schema-repair attempt is permitted by default, using a sanitised validation error, without adding capabilities or widening the candidate catalog. No automatic apply retry on `STATE_CONFLICT`.

## 3. Trust model and subsystem ownership

| Layer | Responsibility | Prohibition |
|---|---|---|
| `wb-semantic` / `wb-registry` | Read-only bounded search over *admitted* local components | No model-originated remote fetching or trust upgrade |
| `wb-contracts` | Proposal/envelope schemas, stable error taxonomy and size limits | No execution or permission grant |
| `wb-operator` (new small crate, or documented existing agent module) | Request construction, provider invocation, parsing, proposal preview | No registry install, direct kernel mutation, hidden tool calls |
| `wb-kernel` | Recheck proposal, apply accepted composition plan, input ingress | No trust in model-selected fields |
| `wb-capabilities` | User/policy authorisation and narrow approval token validation | No inferred grant from prose or RDF |
| Qt/desktop shell | Chat/intent entry, preview, confirmation, visible diagnostics | No direct room mutation and no raw untrusted QML |
| Provider adapter | Natural language → suggested selected candidate, extracted parameters | No secrets, filesystem paths, direct tools or kernel authority |

## 4. Contract boundary

The binding `planVersion: "0.1"` topology JSON from the Architecture Specification remains authoritative. This kit adds **agent-plane-only** transport DTOs (`operator-request`, `operator-suggestion`, `operator-preview`) described by supplemental schemas and constrained to the single-component use case. These schemas are NOT replacements for the canonical composition schema or UI schema. The runtime adapter constructs a canonical plan from the suggestion and current trusted room/candidate data; it MUST validate that plan through the accepted path before displaying it as executable. Existing-room instances and UI refs must be checked against actual accepted contracts.

**Provider suggestion** contains `candidateKey` (opaque host-issued candidate reference, not a trusted filesystem path), `inputValues` (only keys approved by offered input bindings), and a short `explanation` displayed as untrusted text. It contains no executable plan, arbitrary tool call, authority token, room revision or service URL.

**Host proposal preview** includes the exact validated immutable pin, expected room revision, canonical plan digest, optional initial input staging digest, permission summary, evidence of validation, user confirmation requirement and expiry. Exact shape may be implemented with Rust DTOs; freeze a JSON transport contract only after fixture conformance. Never present model explanation as validated evidence.

**Provider boundary:** initial deterministic fixture provider MUST be fully operable offline for repeatable tests. A real network provider is optional for v0.1 but if included it MUST be disabled unless configured/authorised and MUST have request limits, cancellation, timeout, redaction and no tools. No claim that a model infers intent perfectly is permitted.

## 5. Discovery and intent-resolution procedure

1. Receive an explicit user request for a specified room; capture expected room revision and a correlation ID.
2. Enumerate only admitted, executable, permitted local components; filter by search terms/semantic capability references using bounded explicit matching. RDF similarity ranks candidates, it never overrides schemas or pins.
3. Build a maximum-size candidate listing with opaque candidate keys. Reconcile descriptions with authoritative metadata; strip control text or embedded instructions from context.
4. Ask provider for a schema-conforming suggestion. Parse strict UTF-8 JSON, reject duplicate keys and unrecognised properties, enforce byte and item limits.
5. Resolve candidate key against server-created set; verify exact pin and UI availability; resolve fields through actual UI and input schema. Reject invented fields, units and unsupported parameters. Convert common display expressions (e.g. £250,000 and 25 years) only through explicit deterministic, tested adapters and unit rules; never rely on a model's unverified arithmetic.
6. Construct the smallest valid canonical `planVersion: "0.1"` plan, targeting the specified room at its captured revision. Existing room graph must remain valid. Validate permissions/resource quotas and plan without mutation.
7. Display preview and obtain explicit confirmation bound to that proposal, except for a separately reviewed opt-in low-risk policy.
8. Before applying, recheck room revision, registry pin/availability, current grants and approval binding; atomically apply through accepted kernel plan API.
9. On success, submit initial values via accepted host ingress and await committed results. Report stage-specific failures and retain truthful audit evidence. Ongoing UI interaction is direct Qt→Rust→WASM.

## 6. Errors and limits

Stable public errors for this ADR: `NO_MATCH`, `AMBIGUOUS_INTENT`, `MISSING_PARAMETER`, `UNSUPPORTED_REQUEST`, `PROVIDER_UNAVAILABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_INVALID_OUTPUT`, `CATALOG_CHANGED`, `PIN_UNAVAILABLE`, `INVALID_FIELD`, `INVALID_UNIT`, `PLAN_REJECTED`, `APPROVAL_REQUIRED`, `APPROVAL_REJECTED`, `APPROVAL_EXPIRED`, `STATE_CONFLICT`, `INGRESS_FAILED`, `QUEUE_FULL`, `CANCELLED`. Existing kernel/registry error codes retain their meaning and MUST be wrapped rather than forged. No prompt content in public error fields.

Initial suggested limits (not claims of security proof): request <= 4 KiB UTF-8, at most 12 candidates, candidate-context <= 32 KiB, provider reply <= 16 KiB, explanation <= 512 Unicode scalar values, <= 8 initial scalar parameters, one active request per room, 30-second optional external provider deadline. Limit values belong to a host policy configuration and are unit tested; these are provisional until measured. Do not accept arbitrary provider-supplied URLs.

## 7. Consent, data handling and audit

For the initial local mortgage example, only the active user request and the minimal candidate catalog may be supplied to an enabled provider. If external model routing is enabled, the UI MUST clearly identify the external transfer and obtain appropriate user authorisation; an offline fixture implementation remains mandatory. A proposal preview is not a permission grant. Approval is single-use, short-lived, proposal-bound, and invalid on change to room revision, pin or requested effect. No stored secrets in snapshots, tests, logs, or model-visible metadata. Every failed/denied attempt leaves the room unchanged.

## 8. Acceptance and exclusions

Acceptance requires all **OP-001–OP-024** gates in `TEST_MATRIX.md`, two independent reviews (agent/prompt/data security; kernel/state/registry integration), complete pre-existing ABI/IPC/REG/UI/VS1/VS2 regressions, reproducible hosted Linux CI, archived evidence and a successful model-free ordinary reactive edit after the Operator-created room topology is applied. Status remains PROPOSED until those conditions pass.

Deferred: multi-component planning, unbounded graph traversal, creation/publishing of missing components, conversational long-term memory, permissioned tool-using agents, multi-provider failover, model evaluation claims, automatic upgrades, cross-platform UI, remote registries, power-loss DB recovery. These must not be introduced without additional review.

## 9. Alternatives considered

- **Model directly invokes privileged tool APIs:** rejected because it bypasses the accepted validator and creates prompt-injection authority paths.
- **Agent emits the full executable composition JSON:** rejected for v0.1 in favour of a minimal suggestion from which trusted code constructs the canonical plan; may be revisited for multi-component workflows with an explicitly untrusted full-plan envelope.
- **Bake mortgage intent into the host:** rejected; demonstrations may provide deterministic parsing fixtures, but discovery and rendering must remain component-generic.
- **Use an agent in the reactive state loop:** rejected on determinism, latency and cost grounds.
- **Require remote inference for every new room:** rejected in favour of replaceable provider and offline fixture/testing path.

## 10. Rollout and ADR acceptance

1. Land docs and candidate DTO schemas without marking accepted.
2. Implement catalog projection and bounded provider interface behind feature flags.
3. Implement preview, approval, and apply adapter on accepted host APIs.
4. Add Qt Operator entry/preview minimal flow, no new executable UI paths.
5. Run numbered tests and two independent reviews; repair without weakening prior gates.
6. Archive commit, toolchain, exact test commands, reviewer outcomes, hashes, and hosted CI run URL. Set Accepted **only afterward**.

**Non-goal:** ADR-005 does not validate a fully general natural-language agent. The accepted outcome is a safe, interoperable first Operator planning boundary.
