# ADR-006 — Real LLM Provider Integration

**Status:** PROPOSED — pending implementation, independent review, hosted CI and separately reported live-model evidence
**Version:** 0.1 · 2026-10-28
**Prerequisites:** Accepted ADR-001–005 and VSLICE-001–003 (Linux deterministic offline profile).
**Owners:** Operator, security, Qt desktop, verification.

## 1. Context

ADR-005 and VSLICE-003 establish a bounded, offline Operator: read-only discovery of admitted local components, untrusted candidate suggestions, host-generated canonical `planVersion: "0.1"` composition plans, proposal-bound user approval and separate typed initialization. The live provider must replace only the suggestion-generation adapter. The accepted WIT, component manifest, ontology, registry, IPC, Qt UI, approval and room contracts MUST remain unchanged.

The goal is to demonstrate that at least one actual remote model can suggest an existing installed component and its input parameters without creating a new authority or execution path. No claim of correct intent understanding, guaranteed availability, or confidentiality from a third-party provider is implied.

## 2. Decision

1. **Adapter boundary:** Preserve the accepted `OperatorProvider` semantics; add a provider-neutral asynchronous invocation adapter and at least one live implementation (OpenAI Responses API recommended as initial candidate). Additional providers are separate implementations; do not assume API compatibility. The deterministic offline provider remains the default for CI and remains functional with no network or secrets.
2. **No execution authority:** A provider receives only the explicit request plus a bounded, host-built candidate catalog. Its response remains an untrusted `candidateKey` + `inputValues` + short explanation suggestion per ADR-005. No model-originated URLs, filesystem paths, executable plans, tool calls, permission grants, QML, WIT, or direct kernel actions are accepted.
3. **Structured output:** Prefer the selected provider's strict structured-output facility, using a provider-compatible translation of the *existing* accepted suggestion schema. Always verify locally with the canonical strict parser and acceptance rules, including duplicate keys, unknown fields, UTF-8, sizes, semantic value checks and candidate-key membership. Treat refusal, incomplete output, safety filters, unsupported schemas and schema-mismatch as typed failures; provider-enforced JSON shape is not a security boundary.
4. **Endpoint and model selection:** The host owns provider kind, model ID, approved HTTPS origin, API version, and feature capabilities. Use an explicit allowlist for the initial provider, disable redirects and disallow user/model-selected arbitrary endpoints. No generic 'OpenAI-compatible URL' or user-entered arbitrary host in v0.1. Do not silently change models on failure.
5. **Credentials:** Credentials come from a host-managed process environment or OS secret backend. Never put keys in room snapshots, request schemas, logs, Qt bindings, tool results, generated artifacts, model inputs or repository files. Ensure errors and telemetry redact `Authorization`/API key headers and query secrets. No credentials in URL parameters.
6. **Outbound disclosure:** Default to remote inference OFF until a human explicitly enables a provider. Show a clear disclosure that the request and bounded catalog metadata will be transmitted; do not transmit unrelated chat history, personal documents, full RDF literals, local paths or registry files. A human may disable it at any time. A preview/apply still requires the existing user approval independently of model consent.
7. **Budgets:** Enforce request bytes, catalog count, response bytes, max output tokens, wall-clock timeout, concurrency and provider call allowance at the host. Set initial test defaults in §5; make production budget values configurable but bounded by hard caps. Reject over-budget operations before network invocation when possible; abort and invalidate late responses on cancellation/deadline.
8. **Errors and retries:** Distinguish `NOT_CONFIGURED`, `CONSENT_REQUIRED`, `AUTH_FAILED`, `RATE_LIMITED`, `TIMEOUT`, `CANCELLED`, `UNAVAILABLE`, `REFUSED`, `TRUNCATED`, `MALFORMED_RESPONSE`, `SCHEMA_MISMATCH`, `BUDGET_EXCEEDED`, and `PROVIDER_ERROR`. At most one bounded retry for transient transport/rate-limit failures when safe; honor bounded `Retry-After`, never retry authorization failures; a separate single schema-repair request remains subject to ADR-005 limits. No retry may broaden catalog, permissions or execution authority. No automatic apply retry.
9. **Cancellation/revision fences:** Each request carries opaque correlation and request generation IDs, room ID and expected room revision in trusted memory. Late, reordered, cancelled or superseded responses cannot produce an actionable preview or mutate a room. Approval binds to the final host-validated proposal, never to the provider's response.
10. **Audit and observability:** Record provider kind, model ID, request correlation, catalog count, schema identifier, durations, redacted status/error code, token counts when supplied, estimated cost if a verified price table is configured, proposal hash and approval state. Do not claim exact spend from token estimates; do not log prompt or response bodies by default. Redaction must apply to nested errors and debug traces.
11. **UI:** Provide explicit provider selection/status, consent, progress, cancellation, safe errors and a normal ADR-005 validated preview. Keep offline fixture selectable and fully functional; later reactive edits and cold restore MUST generate zero model requests.
12. **Acceptance split:** All `LLM-001`–`LLM-024` deterministic tests, independent reviews, regressions and hosted Linux CI are mandatory. A separately documented live-provider smoke test using an actual provider account and opt-in credentials is required before claiming the **live integration itself validated**, but MUST NOT run in public CI or be a prerequisite for reproducible CI. Do not mark ADR Accepted if the live smoke test has not passed; record 'implementation CI green, live validation pending' instead.

## 3. Ownership and data flow

`Qt request + explicit remote consent` → `wb-operator` bounded local candidate projection → `provider adapter (no tools)` → `strict provider response parser` → `ADR-005 suggestion validation` → `trusted canonical plan preview` → `fresh human approval` → `accepted kernel plan apply` → `separate typed ingress` → `WASM` → `reactive Qt canvas`.

Only the provider adapter uses network credentials. The provider cannot address the registry, host, kernel or renderer. An allowlisted Rust-side networking service is acceptable; credentials and transport MUST NOT be exposed as guest WASI imports. Maintain separation between model-call consent and composition approval.

## 4. Provider-neutral API

The schema files in `schemas/` define supplemental **agent-plane transport and policy fixtures**, not replacements for accepted operator suggestion/preview contracts. Implementation MUST reuse existing Rust DTOs rather than introducing duplicate conflicting structs.

Suggested Rust design (illustrative, adapt to accepted source):

```rust
#[async_trait]
pub trait LiveSuggestionProvider: Send + Sync {
    async fn suggest(
        &self,
        input: BoundedProviderRequest,
        context: InvocationContext,
    ) -> Result<ProviderRawResponse, ProviderFailure>;
}
```

`BoundedProviderRequest` contains only task text, opaque catalog keys and vetted metadata, a schema identity, and fixed prompt instructions. `InvocationContext` contains timeout/cancellation, correlation, budget and provider profile; no room write handle. The adapter MUST NOT return an executable composition plan. The host validates output through the existing suggestion parser and candidate reconciliation.

Represent refusals, incomplete responses, tool-call attempts and usage fields in a normalized response status, not as successful suggestions. Fail closed if unexpected tool use occurs. No streaming partial result may be presented as approved or applied. Streaming, if supported internally, is for progress indication only.

## 5. Initial policy defaults (proposed limits, not provider guarantees)

| Item | Default | Hard cap for v0.1 |
|---|---:|---:|
| Candidate count | 8 | 16 |
| User request UTF-8 bytes | 4 KiB | 8 KiB |
| Catalog JSON bytes | 16 KiB | 32 KiB |
| Provider response bytes | 16 KiB | 32 KiB |
| Output tokens | 512 | 1,024 |
| Total wall-clock deadline | 20 s | 45 s |
| Concurrent requests per room | 1 | 1 |
| Automatic transport retry | 0 | 1 |
| Schema-repair retry | 0 | 1 (ADR-005) |

Tokens and estimated cost are diagnostic; enforce hard limits available to the API and host-side bytes/deadline. Where a provider does not support a requested bound, the adapter must enforce an equivalent host-side limit or report the feature unsupported. Prevent runaway retry chains with a single **overall** deadline and a per-request call budget of at most 3, combining transport and schema repair. Restrict provider responses to a single expected structured suggestion.

## 6. Provider-specific implementation profile

**Recommended initial integration:** OpenAI Responses API with strict JSON Schema response mode; explicitly choose a supported model from configuration and pin tested model ID in the evidence ledger. Verify schema compatibility against provider-supported JSON Schema subset and handle refusal/incomplete fields. Request no tools. The provider's strict response format is an ergonomic aid; canonical host validation remains mandatory.

**Optional second adapter:** Anthropic Messages API using its currently documented JSON-output / strict tool schema facilities, with a separate schema translation and feature-detection layer. Provider-specific refusal and truncation semantics are not assumed interchangeable.

Do not hardcode current model names or prices into security contracts. Models, response-format support and prices change and require current provider verification during implementation. Reference documentation: OpenAI Structured Outputs https://developers.openai.com/api/docs/guides/structured-outputs and Anthropic https://platform.claude.com/docs/en/build-with-claude/structured-outputs .

## 7. Failure and recovery semantics

- Missing consent or credentials → no request, room unchanged.
- Provider failures, refusals, truncated output or incorrect schema → no actionable preview, room unchanged.
- Candidate drift or stale room revision → existing ADR-005 stale-proposal path, no auto-replan or silent selection.
- Successful topology followed by invalid/failed ingress → report partial workflow completion according to ADR-005 and show explicit recovery. Never assert cross-stage atomicity.
- Cancellation after receiving response but before approval → no approval token usable; existing room unchanged.
- Provider is disabled/offline during cold restore → existing committed display remains readable, no network/model/guest call merely for painting.
- Requests in different rooms must not share consent, approval tokens, message bodies or mutable catalog entries.

## 8. Rejected alternatives

- Provider sends full executable plans or calls kernel tools directly: violates established trust boundary.
- Provider-neutral 'arbitrary API base URL' with bearer token: increases SSRF/exfiltration surface.
- Cloud provider required for application startup/restore: breaks local-first requirement.
- Using provider schema compliance as sole validator: insufficient for candidate, permissions and semantic checks.
- Network smoke tests with secrets in default public CI: unreliable and risks exposure.
- Logging raw prompts and responses by default: disproportionate data risk.

## 9. Rollout and acceptance

1. Adopt ADR provisionally and add schemas/fixtures without modifying accepted contracts.
2. Implement mocked HTTP/transport test harness and provider adapter; keep offline default.
3. Implement host-owned consent, credentials, policies, cancellation and UI status.
4. Execute `LLM-001`–`LLM-024`; preserve accepted ABI/IPC/REG/UI/OP/VS regression gates.
5. Obtain independent security/privacy and provider/integration reviews.
6. Run hosted Linux CI with mock transport, no external secrets; archive versions, commands, hashes, redacted logs, reviewer reports and run URL.
7. Run **separate opt-in live smoke** (minimum: successful structured suggestion, explicit malformed/refusal handling as feasible, schema/pin validation and approved real mortgage workflow) using an actual provider account; record model ID, date, sanitized request class, token/cost metrics if available, results and confirmation that no secret entered the artifacts. Never publish raw secrets or private prompts.
8. Mark Accepted **only after** deterministic CI, independent reviews and real-provider validation all pass. The accepted label must specify provider(s) and platform(s) actually tested. If smoke is unavailable, retain Proposed with deterministic CI evidence recorded separately.

**Non-goals:** multi-component planning, model tool calls, remote registry, agent source generation, background autonomous work, broad chat memory, new guest privileges, changes to existing WIT, and cross-platform release packaging.
