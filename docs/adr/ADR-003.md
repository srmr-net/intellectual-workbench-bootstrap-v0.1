# ADR-003 — Component Admission, Local Registry and Dependency Resolution

**Status:** PROPOSED — acceptance requires executable validation and successful hosted Linux CI  
**Version:** 0.1 · 2026-10-25  
**Owners:** `wb-registry`, `wb-semantic`, `wb-contracts`, `wb-storage`, `wb-wasm-host`, security and verification maintainers  
**Dependencies:** Accepted ADR-001 (WIT + Wasmtime) and ADR-002 (host-owned lifecycle, bus and room pins); Component Package and Manifest Specification v0.1; Minimal Semantic Ontology v0.1.  
**Numbering note:** the original ADR-002 text uses “ADR-003” as a placeholder for the future Qt bridge. This document uses ADR-003 for registry/admission as agreed in the roadmap. Track that stale cross-reference as documentation-only cleanup, without renumbering accepted ADRs.

## 1. Context and objective

ADR-001 has validated pure WebAssembly components conforming to `workbench:component@0.1.0` with the accepted `compute(message)` world. ADR-002 has validated lifecycle management, atomic output batches, deterministic propagation, and room-local pins. Neither means that an arbitrary third-party directory is safe to register. A runtime must admit a component **before** it becomes discoverable or eligible for instantiation. The existing package specification makes `component.json` authoritative and requires matching RDF, digests, schemas and optional UI definitions. It explicitly excludes external package dependencies and does **not** standardise a `.wbc` archive container.

**Goal:** a deterministic, auditable and crash-safe **local-directory package admission** workflow that yields immutable content-addressed installations and exact-pinned resolution for ADR-002. No installer execution or remote fetching occurs while validating metadata.

## 2. Decision summary

1. **Keep accepted contracts unchanged.** No modifications to ADR-001 WIT, ADR-002 envelope/lifecycle/room revision contracts, ontology terms or authoritative `component.schema.json`. When contract ambiguities arise, record them and add strict checks rather than inventing a new format. The accepted runtime host is used as the ABI inspection authority; admission never calls `compute` or guest initializers.
2. **Directory bundles only for v0.1.** The input is a local directory matching Component Package v0.1. No normative ZIP or `.wbc` archive bytes, signatures, network resolution, registry federation or dependency solver in this ADR.
3. **Untrusted staging, then immutable promotion.** Read files with strict path traversal controls, validate and copy into a private staging directory, re-open staged content for all checks, then atomically publish the validated content into registry storage. Ensure a crash leaves either no registered release or a fully validated registered release.
4. **Manifest is the execution authority.** RDF and SHACL must agree with manifest identity, ports, artifact, UI and permissions. RDF may not expand capabilities, permissions or executable entrypoints.
5. **The registry does not grant authority.** Installation, capability approval, execution and trust certification are separate. `wb-capabilities` remains the sole grant authority; evidence records are informational until a separate trust policy accepts them.
6. **Identity and resolution are exact.** Unique published release is `(componentId, version)` bound to one immutable SHA-256 artifact digest and an installation record. Resolution by `(id,version,digest)` is required; no latest, floating ranges, silent upgrades, replacements or online lookups. Reject any package with external dependencies in v0.1, including unknown dependency-shaped fields.
7. **Registry read model is host-owned.** Discovery exposes only validated, committed metadata; it does not execute module code. Kernel receives a verified installation handle and pinned artifact bytes, not untrusted paths.
8. **Fail closed.** All malformed, contradictory, unsupported or incomplete packages are rejected without persistent registry side effects. A positive test must include a *real compiled* WASM Component Model fixture; metadata-only mortgage examples are never treated as installable.

## 3. Components and responsibilities

| Subsystem | Owns | Does not own |
|---|---|---|
| `wb-registry` | admission pipeline, immutable store, indices, pins, conflict handling, durable commit/recovery | ABI engine internals, guest execution, permission grants |
| `wb-contracts` | manifest DTO/parser, error model, interface revisions | filesystem operations or policy decisions |
| `wb-semantic` | RDF parsing, SHACL validation and manifest/RDF reconciliation | authorizing ports or privileges |
| `wb-wasm-host` | ABI/component inspection using accepted WIT world; no execution during admission | package identity decisions or registry persistence |
| `wb-storage` | durable registry metadata commit/recovery adapter | granting capabilities |
| `wb-capabilities` | explicit host grants at load/run time | deriving approvals from manifest or RDF |
| `wb-kernel` | resolving exact pinned handles, admission-to-runtime boundary | bypassing registry checks |

## 4. State machine and APIs

Admission attempt states (not public release states): `received -> staged -> validating -> validated -> committed`, or `rejected`/`aborted`. Only `committed` entries appear in search/resolution. The implementation SHALL persist enough journal/marker information to recover after interruption. Registry releases are `installed` and immutable. An installed release may be marked `unavailable` if integrity cannot be re-established; it must never silently fall back to different bytes.

The Rust-facing API SHOULD have equivalent semantics to:

```rust
pub struct ReleasePin { pub id: String, pub version: String, pub wasm_sha256: [u8; 32] }
pub struct ValidatedHandle { /* opaque private registry identity */ }
pub struct AdmissionReceipt { pub pin: ReleasePin, pub record_digest: [u8; 32] }

pub trait LocalRegistry {
    fn admit_directory(&self, source: &Path) -> Result<AdmissionReceipt, AdmissionError>;
    fn resolve_exact(&self, pin: &ReleasePin) -> Result<ValidatedHandle, RegistryError>;
    fn discover(&self, query: &CapabilityQuery) -> Result<Vec<ComponentSummary>, RegistryError>;
    fn read_verified_artifact(&self, handle: &ValidatedHandle) -> Result<Vec<u8>, RegistryError>;
}
```

The opaque handle is not a security token: runtime permissions and room policy are checked independently. `read_verified_artifact` MUST verify the pinned bytes (or check an integrity-guaranteed immutable store with documented threat model) before crossing the WASM host boundary. Registry APIs must be safe for concurrent readers and two concurrent installs of the same release.

## 5. Admission steps (normative ordering)

1. **Discover bounded candidate:** accept only a directory under explicitly allowed roots; enforce admission file count, total bytes, individual file size, depth and time limits. Defaults are implementation policy and MUST be tested; record them in evidence.
2. **Stage safely:** prohibit absolute, parent (`..`), backslash, empty/ambiguous components, links (symbolic and hard-link aliases when detectable), devices, sockets and FIFOs. Block races using safe descriptor-relative operations or an equivalent verified approach, never just a lexical `canonicalize` check followed by later reopening the original file. Reject filenames with case-fold or Unicode-normalization collisions where applicable. No guest code or executable scripts are run.
3. **Parse strict JSON:** UTF-8, reject duplicate keys, validate exact existing `component.schema.json` including `additionalProperties`, `manifestVersion`, `runtime.kind`, interface version and supported manifest shape. Enforce no external dependency declarations. Reject unknown fields instead of interpreting them.
4. **Validate all file references:** presence, normalization, no symlink escapes, optional unreferenced-file policy (choose and test; recommend reject except known documentation). Ensure declared file references are unique and within staging root. Decode port JSON Schemas with local-only references according to package rules; remote `$ref` is forbidden. Detect schema-reference cycles/limits.
5. **Hash artifact:** compute SHA-256 over **raw `logic.wasm` bytes** and compare to the manifest digest. No runtime inference from filename extension. Validate referenced evidence bytes and claims only according to defined contract; evidence does not imply trust.
6. **Reconcile semantic data:** parse Turtle, run SHACL, verify exactly one component identity, exact version, exact input/output port set (including names/direction/schema refs/semantic types/optional units), artifact path/digest, optional UI reference and semantic permission claims. An unsupported nonempty permission vocabulary must fail closed until the permission ontology and policy mapping are approved.
7. **Validate UI where present:** parse abstract UI document against the pinned UI schema, reject executable QML/JS, and cross-check bindings against the manifest's available ports. Do not fabricate an interface schema where not yet formally adopted; block UI-bearing packages until the schema/bindings contract is present and tested.
8. **Inspect Component Model ABI:** reject core wasm modules, malformed components, missing exports, wrong WIT world, or incompatible `compute` type; do not invoke any guest function. Enforce allowed imports against the pure world; initial policy rejects WASI and host-service imports. Apply bounds to component compilation/type-checking and report it separately from guest execution budgets.
9. **Authorize admission policy (not execution):** verify local source/store policy, disk quota and provenance policy. Untrusted origin cannot become `reviewed`/`verified` solely through assertions in evidence.
10. **Commit atomically:** create immutable content-addressed file storage and a durable index record with a strict write ordering (temp write + fsync, atomic rename, directory sync, metadata transaction/commit marker). If store and index use distinct durability domains, recovery must never expose a partial install. A component visible to `discover` must be resolvable and integrity-checked.

## 6. Identity, conflicts, pinning and removal

- `componentId` is case-sensitive, version is exact SemVer as defined by the existing schema, and artifact digest is lowercase hex SHA-256. The manifest and RDF identity MUST agree.
- Exact repetition of an existing `(id,version,digest)` is idempotent and returns the same logical release. `(id,version)` with a different artifact digest returns `RELEASE_CONFLICT`, never overwrites in place.
- Identical WASM bytes do not justify merging two distinct `(id,version)` releases: each has separate metadata and assurance claims.
- Rooms pin `(id,version,digest)` as established by ADR-002. Resolve failures return `COMPONENT_NOT_FOUND` or `INTEGRITY_FAILURE`, not a compatible substitute.
- Removal of a pinned release is rejected or deferred; garbage collection is allowed only after durable live-pin reference checks and no active instance depends on the artifact. v0.1 MAY omit removal/GC entirely.
- Version constraints/ranges and transitive dependency graphs are deliberately **not** supported in v0.1. That is a later extension with its own conflict-resolution and lockfile ADR.

## 7. Errors and reporting

Admission SHALL emit stable machine-readable error codes and a bounded, sanitized location (`component.json` JSON Pointer, `capabilities.ttl` subject, package-relative file path). At minimum: `INVALID_MANIFEST`, `UNSUPPORTED_VERSION`, `INVALID_PATH`, `MISSING_FILE`, `DIGEST_MISMATCH`, `SCHEMA_VIOLATION`, `RDF_INVALID`, `SEMANTIC_MISMATCH`, `ABI_INCOMPATIBLE`, `UNSUPPORTED_DEPENDENCY`, `CAPABILITY_DENIED`, `RELEASE_CONFLICT`, `ALREADY_INSTALLED` (non-error idempotent result permitted), `INTEGRITY_FAILURE`, `QUOTA_EXCEEDED`, `REGISTRY_IO`, and `COMPONENT_NOT_FOUND`. Map these to existing generic contract errors where necessary without silently changing accepted shared DTOs. No host absolute paths, credentials, raw secret content or guest stack traces in public errors.

## 8. Security, reliability and explicit limitations

- Successful admission means **structural and policy-valid package**, not safe, correct, reviewed or formally verified software.
- Unsigned local developer packages are supported as untrusted; no signature verification or source authenticity claim in v0.1.
- Admission-time Wasmtime compilation may allocate native memory; execute inspection with bounded external worker isolation or documented process-level quotas before admitting hostile packages in production. A time limit around an in-process compilation call alone is not a memory sandbox.
- Strong filesystem races and crash/power-loss durability require deliberate tests; a simple temp-write-plus-rename without index recovery is insufficient.
- The component's WASM may still trap or produce invalid output during runtime; ADR-001/002 continue to enforce execution budgets, output validation and failure isolation.
- Semantic compatibility for composition is a separate kernel decision: admitting a package does not certify that all semantically adjacent ports can be connected.

## 9. Validation gates (REG-001–REG-020)

| Gate | Scenario | Passing evidence |
|---|---|---|
| REG-001 | compiled valid pure guest bundle admitted | exact pinned resolution and bytes available, no guest execution |
| REG-002 | strict manifest rejects unknown fields, duplicate JSON keys and invalid version | typed rejection, no index entry |
| REG-003 | path traversal, absolute, symlink and nonregular file attacks | no escape/read/commit; evidence of race-safe strategy |
| REG-004 | missing referenced schema/module and malformed local JSON Schema | reject, no index entry |
| REG-005 | raw WASM digest mismatch and post-admission tamper | reject on admission/read, no replacement bytes |
| REG-006 | bad Turtle and SHACL violation | reject with semantic location |
| REG-007 | manifest/RDF identity, port, schema, semantic type, unit and digest mismatches | each rejected independently |
| REG-008 | UI absent accepted; UI present validated against **pinned** UI schema | invalid binding or executable UI rejected; if schema unresolved, explicitly block UI packages |
| REG-009 | nonempty unknown permission request or RDF mismatch | fail closed, no automatic grant |
| REG-010 | wrong WIT/component encoding, imports or type | rejected before guest execution |
| REG-011 | artifact installed twice identically | idempotent identical pin/index |
| REG-012 | same id+version different digest | conflict, original release intact |
| REG-013 | exact pin resolves; missing/mismatched pin rejects | no fallback/upgrade |
| REG-014 | interruption before rename, after file write, before/after index commit | recover with zero partial visible records |
| REG-015 | concurrent installer/readers for same release | one correct installed record, no corruption |
| REG-016 | registry discovery does not instantiate guest or reveal rejected items | host-only metadata read |
| REG-017 | dependency-shaped declarations or remote refs | explicitly unsupported/rejected |
| REG-018 | forged assurance/evidence cannot elevate trust | unreviewed admission remains unreviewed |
| REG-019 | admission quotas, filesystem races and oversize package | bounded failure, no unsafe resource exhaustion |
| REG-020 | ADR-001/002 regressions and clean hosted Linux CI | full existing ABI/IPC suites, Clippy, format, contracts and archived evidence pass |

All tests must be non-ignored and exercise production code paths, not mock away the security-critical checks. For REG-014 and REG-019 use injection points and adversarial fixtures; report what was simulated and what was exercised against real OS primitives. Missing prerequisites are **blocked**, not passed.

## 10. Acceptance and rollout

**Proposed → Accepted** only after: (a) REG-001–REG-020 mandatory gates pass (or any deliberately blocked feature is explicitly removed from v0.1 supported surface by a documented ADR amendment), (b) independent review of filesystem traversal, durability, concurrency and ABI/type-check admission, (c) clean hosted GitHub Linux CI referencing the exact commit, (d) evidence report with commands, pinned versions, artifacts/hashes and limitations, and (e) accepted ADR-001 WIT and ADR-002 semantics unchanged. A green workflow file without an executed hosted run is not evidence.

Adoption scope is the **local registry vertical slice**. Archive formats, signing, federation, remote registries, external dependency resolution, production isolation for hostile package compilation and richer permission vocabularies remain explicitly deferred.

## 11. Executable local profile (implementation; acceptance pending)

The implementation uses a Linux host-private directory store rather than a second
metadata database: immutable objects are addressed by SHA-256 of a versioned
installation record (including every payload file hash, canonical checked metadata
and an untrusted-local provenance class). One atomic release marker per exact
identity/version is the only index authority. Both rename parents and every file
and nested directory are synced in the documented order. A process-wide OS flock
serializes admission, recovery and integrity reads across independent processes.
No removal/GC API exists; recovery only removes never-published objects/stages.
Corrupt published releases stay unavailable. If any marker or referenced record
cannot be integrity-validated, orphan cleanup pauses rather than destroying
potentially pinned bytes. Same identity/version with changed
metadata also conflicts rather than silently replacing semantic or assurance data.

New trusted admission SHACL shapes implement the existing package specification;
they do not modify ontology terms or upstream reference material. Python
jsonschema/rdflib/pySHACL provide metadata validation inside a bounded native
worker. The original Wasmtime `Host::register` is the separate bounded ABI worker:
no guest initializer or compute function runs during admission. A regression uses
a correctly typed component with an actually trapping initializer to prove this.
Native worker quotas are separate from guest execution limits, and do not claim
a complete hostile-parser OS security sandbox.

**Supported surface amendment:** UI-bearing packages are deliberately rejected.
The G0 UI schema exists, but portable package binding ownership/rebinding semantics
remain provisional (ADR-011). REG-008 covers rejection of all UI packages and
acceptance of absent UI, as allowed by its original gate. Nonempty permissions
remain denied pending approved vocabulary/policy mapping. JSON Schema supports
acyclic package-local file references and object-member JSON pointers; array-index
pointers, recursive schemas,
IDs/anchors/dynamic references and non-2020-12 dialects are rejected rather than
reinterpreted. No new WIT, manifest, ontology, shared IPC or grant contract is added.

Defaults, exact write ordering, public APIs and threat model are documented in
`crates/wb-registry/README.md`. ASCII-only paths reject case-fold/normalization
ambiguity and all links/nonregular entries. Limits cover 64 directory/file entries,
2 MiB/file, 8 MiB/package, depth 8, 128 releases and 128 MiB logical store bytes,
with a reserved package/metadata staging allowance. Workers use 2 GiB address
space, 30 seconds CPU/wall, 4 MiB output, 64 descriptors, no core dumps and parent-
death termination. Staging checks elapsed time between filesystem operations;
hung filesystem calls are not hard-time-bounded. Record/index writers enforce
the same size ceilings as readers before promotion.

`REG-014` uses real SIGKILL/reopen at seven production checkpoints, including after
marker rename before directory sync. This validates process-crash recovery, not
physical power failure. The filesystem must honor atomic rename/fsync; the store
and worker tools are trusted and private to the host UID. Same-UID store sabotage,
hostile mounts, block-level disk quota accounting and production parser/compiler
security isolation remain deferred. Exact-read rehashing detects ordinary store
corruption; it is not authenticity protection against a privileged store writer.

ADR status remains Proposed until named REG gates, independent reviews, clean
hosted Linux execution and downloaded artifact verification are recorded in
[evidence/ADR-003-results.md](evidence/ADR-003-results.md).
